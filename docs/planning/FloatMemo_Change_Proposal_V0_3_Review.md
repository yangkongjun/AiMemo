> **审核结论先看：拟在安卓 V0.2.6 上增加可配置的生成上限、正文插图及完整图片备份，并把 AI 搜索改为“有范围、有输入预算、取命中片段、单次请求”的流程。**
>
> 日期：2026-10-27。用户已明确批准本方案并开始实施；结果与验收边界见[交付记录](../releases/V0_3_0.md)。以下保留审核时的方案内容。原状态：**待用户审核，尚未实施**。这一轮只生成报告，不修改应用代码、数据库或签名，不生成新 APK。报告中的默认值、类名和验收目标均为提案。

## 一、范围及需要你确认的产品取舍

本报告针对当前归档的 **安卓 V0.2.6**。Windows 桌面版不在这次改动范围内，不能把安卓的文件变更直接套用到桌面工程。

| 需求 | 本次拟交付 | 明确边界 |
| --- | --- | --- |
| 扩大 token 数 | 在 AI 设置中分别配置整理、搜索的生成上限；增加读取等待设置与用量说明 | 不把配置值当作服务商真实上限；不保证3000字一定成功；不自动放大预算或增加重试 |
| 插入图片 | 从系统选择图片，在光标位置插入；预览显示、点开查看；本机持久保存；完整备份和恢复 | 首版不做 AI 识图、OCR、相机拍摄或剪贴板粘图；编辑模式显示图片占位符，不是所见即所得富文本 |
| 控制 AI 搜索成本及时间 | 按范围先本地筛选、总摘录预算、命中片段、最多一次远程请求；同条件短期缓存 | 不引入向量服务、额外 embedding 接口或自动多轮补搜；不能保证每次都找到所有相关笔记 |

**最重要的审核项是第二项：首版图片只保存和显示，不自动交给 AI 识别。**图片中未转录成正文的文字，本版无法靠 AI 搜索找到。你自己在正文写的图片说明仍可搜索。

## 二、我核对到的当前实现

以下为源码事实，不是新方案已经完成的描述。

| 当前行为 | 源码依据 | 带来的限制 |
| --- | --- | --- |
| 正式整理与 AI 查找的输出上限都写死为3000，短测试为64 | AiClient.java 的 analyze / search / testConnection | 用户不能在界面调生成预算 |
| 每篇按最多约10000个Java字符串字符分段，单篇输入上限120000 | AiDocument.chunks / AiClient.analyze | 3000字常规纯文本通常是一段；更长笔记可能多次调用 |
| 读取等待为60000ms，连接等待12000ms | AiClient.chat | 增大生成预算后，可能先碰到等待限制 |
| AI查找从repo.all()取全库笔记，挑最多30篇，每篇只发送开头1400字符 | MainActivity.semanticSearch / SearchEngine.candidates / AiClient.search | 最坏正文片段约42000字符；后半部分的关键内容看不到 |
| 一次AI查找把候选合并为一个请求；普通输入只做本地搜索 | MainActivity / AiClient | 100篇笔记不等于100次搜索请求，但请求可能较大 |
| 笔记正文是字符串；编辑器为EditText；预览为自有Markdown文字渲染 | Note / NoteEditorActivity / FloatingNoteWindow / Markdown | 当前没有图片附件模型和图片显示流程 |
| JSON备份schemaVersion为2，保存笔记、文件夹、历史与纠正记录 | NoteRepository.exportJson / importJson | 不包含图片文件；只插图片路径不能构成完整备份 |
| 结果接收主要检查原文revision、人工锁定，配置另用epoch隔离 | ResultGate / NoteRepository / AiClient | 新增图片和缓存时必须维持这些保护 |

当前3个不同限制需要分开：**生成上限、模型总上下文容量、每日请求次数**。本次新增的是每次请求的生成预算设置，不是购买更多服务商额度，也不是精确的每日token封顶功能。

## 三、token配置和长笔记：具体修改

### 3.1 设置页拟增加什么

基础设置保留现有地址、模型、Key和每日次数，在其下增加“生成与等待”。较少使用的搜索预算放入高级设置。

| 字段 | 拟定默认值 | 本机允许填写范围 | 作用 |
| --- | --- | --- | --- |
| 单次整理生成上限 | 8192 token | 512–32768 | 每段笔记整理的max_tokens |
| 单次搜索生成上限 | 4096 token | 512–16384 | 合并搜索请求的max_tokens |
| 响应读取等待 | 120秒 | 30–300秒 | 读取等待；不是整个任务的绝对总时长 |
| 搜索候选上限 | 10篇 | 5–30篇 | 本地筛选后最多交给AI的笔记数 |
| 搜索正文摘录预算 | 12000字符 | 2000–30000字符 | 多篇候选正文片段的合计上限 |

范围是**本次拟定的应用保护范围，不是魔搭每个模型都支持的参数范围**。如果服务不接受8192，应显示服务错误并允许用户调小；不偷偷换模型或地址。上限不是固定消耗，最终用量以服务返回为准。

保留短诊断的64 token预算及“已响应但测试输出达上限”的区别，不让每次连通测试也消耗大预算。现有每日次数继续独立生效。

### 3.2 修改哪些文件

| 文件 | 计划修改 |
| --- | --- |
| AiConfig.java | 增加各设置的读取、默认值、范围校验和原子保存；升级时旧Key和启用状态保留；没有新字段时使用上述默认值 |
| AiSettingsActivity.java | 增加输入、预设值、单位及说明；数值非法不保存；用户保存后下次请求生效 |
| AiClient.java | 移除两处写死的3000；整理与搜索分别使用配置；读取超时取配置；在一次操作开始时固定所用配置快照 |
| ApiResponse.java | 保留截断结果拒收；提示同时考虑生成上限和总上下文限制，避免统一归因为“换模型” |
| DiagnosticRecord.java / DiagnosticActivity.java | 记录请求上限、实际用量、结束原因、读取等待；区分本机限制与服务错误；不写入正文、Key或推理全文 |
| AiDocument.java | 保留现有逐段整理及原文引用规则；接入不包含图片占位符的可整理文字；本次不改成每3000字再自动拆一次 |
| 拟新增 RequestOptions.java | 一次请求所用的配置快照及纯逻辑校验，便于测试；不含可导出的Key字段 |

### 3.3 行为约定

- 修改生成上限不会自动重跑所有已完成笔记。用户可对需要的笔记点“重新整理”。既有待整理队列仍遵循原后台逻辑。
- 配置改变仍更新epoch；已发出的请求可能产生用量，但其旧配置结果不覆盖新状态。
- 3000字笔记不会因为新增配置而默认被拆成多次。保留约10000字符的原分段边界，不新增隐藏的续写请求。
- 如果finish_reason为length，记录实际情况、保留原文，不把截断JSON保存成完整结果。提供明确的手动重试路径，不自动把8192倍增为16384再收取一次用量。
- 不在本版自动启用/关闭某个服务商的思考模式；不同服务参数需要实际兼容性确认，不能照另一家服务的文档盲传。

## 四、插图：从选择到保存、预览和恢复

### 4.1 你将看到的操作

1. 在普通笔记编辑页点“插入图片”，通过系统文件选择器选一张或多张图片。
2. 图片先复制到应用自己的附件目录；只有复制与保存成功才加入笔记。不是只记一个相册临时路径。
3. 在光标处插入图片占位符，例如 `![图片](attachment://图片ID)`，不改动周围原有文字和换行。编辑模式可通过占位符调整位置；预览模式在对应位置显示图片块。
4. 点预览中的图片可打开内部查看页，支持缩放查看。可删除正文图片引用；物理文件清理需核对其他笔记、保留历史和导出是否仍引用。
5. 原相册图片删除后，应用已保存的副本仍应能显示。卸载应用仍会删除其私有附件，完整备份必须另存。

首版从完整编辑页插入；悬浮窗也能预览已有图片，并提供进入完整编辑页的操作。**不在悬浮窗上直接启动图片选择器**，减少覆盖层权限和窗口焦点问题。编辑模式不承诺直接拖拽图片或富文本混排。

### 4.2 格式和拟定边界

| 项目 | 首版提案 |
| --- | --- |
| 图片格式 | JPEG、PNG、静态WebP；不承诺HEIC、动图和远程图片链接 |
| 单张原文件 | 最多20MiB，超过时明确提示，不静默丢图 |
| 单篇图片 | 最多20张，原文件合计最多100MiB |
| 显示策略 | 原文件保留；预览按控件大小采样加载，避免把所有原图同时解码进内存 |
| 图片识别 | 不做OCR或AI识图；不上传图片、图片路径或Base64给模型 |

这些是拟定边界，可在审核时调整。实际像素边界、极大尺寸图片的拒绝或采样策略，需要在实施中按可用内存检查并验收，不能只看压缩文件大小。

### 4.3 数据和代码怎样改

| 文件或新模块 | 计划修改 |
| --- | --- |
| Note.java | 增加附件元数据集合及AI文字来源指纹；copy、toJson、fromJson一起更新；旧笔记没有字段时按空附件读取 |
| 拟新增 Attachment.java | 图片ID、MIME、字节数、宽高、内容SHA256等；正文只存稳定ID，不存Base64或设备绝对路径 |
| 拟新增 AttachmentStore.java | 私有目录内的原文件、采样预览、暂存、完整性检查和引用核对；后台文件IO |
| 拟新增 NoteBodyParser.java | 识别本地图片占位符、文字段和代码块；代码块里的类似文字不当图片；产生AI可用的原文文字与原位置映射 |
| 拟新增 NotePreviewRenderer.java | 在普通文字Markdown块之间显示图片块，异步加载、限制内存；只加载登记在本笔记中的本地附件 |
| NoteEditorActivity.java | 插图入口、选择结果处理、光标位置、占位符、删除、预览状态恢复；导出/分享文字时说明图片不包含在其中 |
| FloatingNoteWindow.java | 复用新预览组件，支持已有图片；控制小窗口中图片尺寸，保留原编辑操作 |
| Markdown.java | 保留文字Markdown能力，交给新预览组件渲染文字块；不自动拉取网络图片 |
| 拟新增 ImageViewerActivity.java / AndroidManifest.xml | 注册仅应用内部可打开的查看页，以附件ID定位；不接受任意文件路径 |
| NoteRepository.java | 附件元数据的事务保存、图片变更与文字变更区分、附件引用快照及搜索缓存失效通知 |

先用系统 `ACTION_OPEN_DOCUMENT` 选择指定文件并复制副本，覆盖现有minSdk26范围，不申请读取整个相册的广泛权限。本轮不因图片功能大幅提高最低Android版本，也不引入网页编辑器。

### 4.4 图片变动不能破坏AI原文保护

这是本次必须处理的联动，而不只是界面变化：

- 图片二进制、内部ID和路径不送入整理或搜索请求。正文中图片占位符由解析器识别并排除；真正的用户文字不进行改写。
- 只增删图片、参与AI的文字和标题完全不变时，不新触发一次整理；现有文字整理仍可继续使用。
- 为此保留原revision，同时增加“参与AI的文字来源指纹”。只有在图片变动、文字指纹完全一致、来源摘录仍能定位、未被删除或人工锁定、配置epoch一致时，才允许接收原在途文字结果。不能仅以“发生过图片操作”为由放宽原文校验。
- AiDetailActivity.java 的原文定位，以及MainActivity.java对旧结果的判断，同步改用新的来源映射/有效性判断。即使一段文字中间插入图片，也不能把引用位置跳到另一段。
- 只含图片而无可整理正文的笔记，提示“暂不支持图片内容整理”，不调用模型生成猜测的要点。

相应涉及 AiClient、AiDocument、AiDetailActivity、ResultGate、NoteRepository、MainActivity 的联动。旧笔记升级时只有能验证仍对应当前文字的AI结果才补记有效指纹；不为迁移自动发请求，也不擅自把旧结果标成最新。

## 五、图片备份：必须与插图一起交付

### 5.1 新增完整备份格式

主菜单增加“导出完整备份（含图片）”和相应导入。使用ZIP容器，至少包含：

| 条目 | 内容 |
| --- | --- |
| manifest.json | 备份格式版本、附件清单、大小和SHA256 |
| notes.json | 新版schemaVersion=3的笔记、分类、历史及纠正数据 |
| assets/ | 被笔记及所保留历史引用的原图片文件；不必保存可重建的缩略图 |

现有SQLite表以JSON保存笔记，可为新字段提供兼容读取；必要时增加附件索引表，不删表、不清库。**数据库版本、JSON schema版本和ZIP容器版本分别处理**，不混为一个数。

旧schemaVersion1/2的JSON继续能导入。现有单独JSON出口保留为明确标注的文字/元数据导出，不宣称带图片文件；含图笔记优先完整ZIP备份。旧版软件不保证能读新版含图备份。

### 5.2 需要修改的入口与恢复规则

- `NoteRepository.java`：提供一致的导出快照与schema3读写，保留当前冲突副本、历史及人工纠正逻辑。
- `ImportPolicy.java`：把附件内容身份和新增有效性信息纳入重复/冲突判断；避免“文字一样、图片不同”被误当相同记录。
- 拟新增 `BackupArchive.java`：流式导出/导入，不把全部图片Base64塞进原JSON。先验证清单、文件、摘要和空间，暂存后才合入。
- `MainActivity.java`：新菜单、文件选择、进度和导入结果；在后台执行文件处理。JSON与ZIP按实际格式识别，不只看扩展名。
- 图片ID冲突时重映射正文、附件、历史与纠正记录中的引用，再生成导入回执。重复导入应跳过已完整恢复的相同内容；若同名资产实际缺失，要能修复而不是永久跳过。
- 文件和数据库不是天然的同一事务：新图片先就位、数据库再提交，并保留恢复日志；失败或中断时不能覆盖既有图片，重启时只清理本次未被成功数据引用的新增暂存文件。
- 导入条目只允许进入应用附件目录，校验相对路径、总量和单张大小。首版拟限制压缩包500MiB、展开内容1GiB，超限在写入正式数据前停止。

验收必须实际做“含图导出 → 在隔离测试环境恢复 → 对比正文、图片SHA256和历史”。不能仅以能生成一个ZIP文件判定备份已完成。

## 六、AI搜索：改变筛选和发送方式

### 6.1 用户看到的流程

普通输入继续只做本地搜索。点击“按意思用AI查找”才开始远程请求，依次执行：

1. 明确搜索范围。主页为“全部笔记”时搜全库；选中主题时默认搜当前主题，并可显式切换到全部。
2. 在手机本地对范围内的标题、正文、标签和主题做排序；不发API。缓存本地计算所需数据，文字或相关元数据变化时更新。
3. 从候选正文中找命中位置，提取最多3段附近原文，单篇合计不超过1200字符；没有文字命中时才退回开头片段。
4. 最多选配置数量的笔记，并受正文摘录总预算约束。预算不足就减少或缩短片段，不自动拆成第二个远程请求。
5. 把候选及实际摘录合并为一次请求；AI返回的每个quote必须完整属于某一段已发送原文，并能定位到同一笔记，不能跨两个拼接片段制造连续引用。
6. 显示检查范围、候选数、实际摘录字符数、本次请求数和耗时；失败继续展示本地结果并说明原因。

默认从当前的“最多30×1400=42000正文字符”变为“最多10篇、正文合计不超过12000字符”。这降低的是发送上界，不是对耗时按比例变快的保证。输入还包括提示词、标题、标签、查询和JSON结构，**12000不是整个HTTP正文或精确token上限**；这些元数据也会单独限长，并在诊断中记录实际请求长度与服务返回的token用量。

### 6.2 修改哪些文件

| 文件或新模块 | 计划修改 |
| --- | --- |
| MainActivity.java | 本地排序移入后台；范围选择在筛选候选前生效；新的准备/请求/结果状态；生命周期和旧查询隔离 |
| SearchEngine.java | 保留本地文字搜索及相关笔记；改进候选排序，范围与上限由参数传入；处理标题/标签/主题命中及有正文后段命中的情况 |
| 拟新增 SearchPlanner.java | 生成带noteId、文字版本和原文起止位置的候选计划；命中窗口、片段合并、UTF-16边界和总预算控制 |
| 拟新增 SearchCoordinator.java | 同条件请求合并、最多一个活动AI搜索、结果短期缓存；Activity重建不自动再发相同请求 |
| AiClient.java | 接收结构化候选及多个原文窗口，而不是截取前1400；更新检索提示词和返回校验；搜索仍一个HTTP请求 |
| NoteRepository.java | 新增与检索有关的内容变更代号；正文、标题、主题、标签、删除、导入、AI派生标签改变时使缓存失效 |
| AiSettingsActivity.java / AiConfig.java | 候选数、正文预算、搜索生成上限设置 |
| strings.xml | 删除写死的“前1400字符”；显示真实范围、检查条数、正文摘录量及缓存状态 |
| DiagnosticRecord.java / DiagnosticActivity.java | 记录范围、计划候选数、实际候选数、正文预算、实际长度、缓存命中、本次搜索请求数与分阶段耗时 |

新增类名为提案，实施时可以小幅合并，但职责和验收边界不变。本轮不引入向量数据库、额外模型服务或新的API Key。

### 6.3 缓存与次数约定

- 拟设内存缓存20条、有效期5分钟，不写成永久搜索历史。相同查询、范围、正文及元数据版本、配置和预算才可复用。
- 只按笔记revision检查不够：当前修改标签/主题不一定提高正文revision。因此新增检索内容变更代号，不能漏掉这些变更。移动悬浮窗位置、改外观不必清空搜索缓存。
- 缓存命中、空库和普通文字搜索，远程请求为0；未命中缓存的一次AI搜索最多请求1次，不自动补搜、重试或并发拆包。
- 查询、范围或数据在请求期间变化，旧结果不覆盖新页面。已提交的请求可能仍计数，界面取消不承诺服务商未收费。
- 后台自动整理可能独立发请求。日志必须按“笔记整理”“AI查找”“连接测试”分开，不能把后台次数说成本次搜索次数。
- 有限候选筛选仍可能漏掉表达完全不同的笔记，不能宣称搜索已经变成全库语义检索。长期如需更高找回率，需另行评估索引方案。

### 6.4 已确认补充：命中位置附近的截取规则

用户认可“优先截取命中位置附近的内容”，将其作为本次搜索改造的明确实现要求。这里的“命中”指手机本地对查询词及其字符组合定位到的原文位置，不增加一次模型调用来找位置。

举例：一篇3000字的笔记，关键句在第2200字附近。旧版只发前1400字符，看不到该句；新版在它入选候选后，发送第2200字附近的实际原文，初始窗口可按前后约300字符取，再结合句子或段落边界调整。

- 同一篇多处命中时，按相关性选择、合并重叠窗口，最多3段且正文合计不超过1200字符。
- 所有候选仍受搜索正文总预算约束。先为高排名候选分配基本片段，再按剩余预算分配额外窗口，不能因一篇长笔记耗尽全部预算。
- 没有直接正文命中时回退到开头片段，并记录回退原因；不能声称已经覆盖整篇或解决所有同义表达。
- 每个窗口保留笔记ID、文字版本、原始起止位置；不得改写原文。
- quote必须完整属于某个独立窗口，并能用来源映射回到该笔记原文；跨两个窗口拼成的quote拒收。
- 诊断记录窗口数、合计字符数和是否回退，不写入完整原文片段。
- 增加明确验收例：第2200/5000字附近命中、多个重叠命中、无直接命中、含emoji边界、总预算不足、跨窗口伪造引用。位置截取不得增加搜索远程请求次数。

## 九、升级与回退原则

升级前先从现版导出笔记备份。新版读取旧笔记时不批量改正文、分类或人工纠正，不自动重新整理全部已完成笔记。包含图片后主备份改用完整ZIP；手机私有数据仍不会因为项目归档而自动备份。

新版媒体数据不能假设由旧版APK正确读写。若需撤回功能，优先在兼容新数据的修复版本中处理，不通过卸载或强行降级来回退。升级前的旧备份不含升级后新写入的内容，不能拿它覆盖新数据而声称无损。
